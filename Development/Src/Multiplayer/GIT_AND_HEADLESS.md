# Git в корне и headless-тестирование

## Git

Репозиторий теперь находится прямо в `/mnt/ntfs1/OLs/OL1`, копировать файлы больше не нужно.

```bash
cd /mnt/ntfs1/OLs/OL1
git status                                     # быстро: корень запрещён в .gitignore
git add -u                                     # изменения отслеживаемых файлов
python3 Development/Src/Targets/git_track.py   # что ещё изменилось, но не отслеживается
python3 Development/Src/Targets/git_track.py --add
git commit -m "..."
git push
```

### Почему не белый список по расширениям

Первоначальная идея `!Development/Src/**/*.cpp` опасна. В `Development` около 21 тысячи исходников, а отслеживаются только те, что отличаются от оригинала. Один `git add .` отправил бы всё дерево UE3 в публичный `OpenOL`.

Поэтому:

- `.gitignore` запрещает всё по умолчанию. Отслеживаемых файлов это не касается, и `git status` не сканирует дерево.
- Разрешены только собственные каталоги: `Multiplayer/{Classes,Inc,Src,Tests}` и `Multiplayer/*.md`.
- Минус: правка ещё не отслеживаемого файла движка не видна в `git status`. Эту проблему закрывает `git_track.py`: он сравнивает дерево с оригиналом в `/mnt/ntfs1/OLs/Development`.

### Что заменяет diffs.sh

| diffs.sh | Сейчас |
|---|---|
| Копирует изменённые файлы в `~/OL1_changed_files` | Не нужно |
| Находит изменённые и новые файлы | `git_track.py` |
| Список `EXTRA_FILES` (конфиги, `.upk`, локализация) | Файлы отслеживаются и видны в `git status` |
| `Missing` только пишет в лог | `git add -u` фиксирует удаление |
| `diff_output.patch` | `git diff` |

`git_track.py` запускается вручную перед коммитом. Первый запуск после холодного старта занимает около 2 минут (21 тысяча файлов на NTFS), дальше около 3 секунд. Поэтому его можно вызывать из `pre-commit` хука, но хук пока не установлен.

Настройки репозитория, которые не хранятся в git: `core.fileMode=false`, `core.autocrlf=false`. На другой машине их нужно задать заново.

### Что не изменилось

- `~/OL1_changed_files` остаётся резервной копией; после проверки её можно удалить. **Не пушьте из неё:** ветки разойдутся.
- `diffs.sh`, `diffs_old.sh`, `diff_output.patch` пока лежат в корне. Git их игнорирует.
- `Multiplayer/server` остаётся отдельным репозиторием `OpenOL-Relay`. Общие файлы сервера (`server.c`, `server.h`, `db.*`, `relay_compat.h`, `openol_protocol.h`) обязаны совпадать с `External/openol_relay`, это проверяет тест. После правки сервера копируйте их в оба места.

### Решение, которое ещё нужно принять

Как сделать один исходник сервера вместо двух одинаковых копий:

1. **Сабмодуль `OpenOL-Relay`** (рекомендую): `External/openol_relay` собирается из него, сабмодуль закреплён на коммите. CI потребует `submodules: true`.
2. Перенести сервер в основной репозиторий и закрыть `OpenOL-Relay`.

Отложено, потому что затрагивает публичные репозитории.

## Headless-тестирование

Заметка про headless в памяти относилась к mpv. Для OL инфраструктура начинается с `Multiplayer/Tests/`.

Порядок по соотношению пользы и стоимости:

### 1. Протокольные тесты без игры — готово

```bash
python3 Development/Src/Multiplayer/Tests/test_relay.py -v
```

Собирает сервер с ASan и UBSan и проверяет его по UDP: разбор, снимки новичку, арбитраж, фаззинг случайными пакетами и пакетами с верным заголовком. Занимает ~10 секунд. Уже нашёл ошибку, которая не была заметна при чтении кода: циклы CLI и GUI автономного сервера не вызывали `server_drain_snaps`, и новичок не получал снимки.

Следующие шаги:
- Запись настоящих пакетов и воспроизведение как эталон (golden-файлы).
- Сетевая деградация через `tc netem` в отдельном network namespace (`tc` установлен): 5–10% потерь, 200 мс. Потребуется для этапа 1.
- Сценарии гонок на уровне арбитра (два одновременных `REQ_TRIGGER`) — для этапа 3.

### 2. Фаззинг клиентского разбора

Разбор пакетов клиента вынести из `AMultiplayerController` в функции без зависимости от движка (`FNetReader`, этап 1). Тогда те же фаззеры смогут проверять клиентский код на Linux, без Wine и MSVC.

### 3. Маркеры в логе

Тестовая карта с актором `OLTestRunner` выполняет сценарий и пишет `[TEST] PASS/FAIL <name>` в `Launch.log`. Python-раннер разбирает лог. Подходит для `OLBot`: переходы состояний, путь по NavMesh, зрение.

### 4. Headless-сервер игры (разведка SimNode)

В этой сборке режим есть, но запускается токеном, а не флагом:

```
OLGame.exe server <map>?Game=...?ListenPort=7777 -log -nosteam -nohomedir
```

См. `_startgameasserver.bat`, `Launch/Src/LaunchEngineLoop.cpp:2659`, `Engine/Src/UnEngine.cpp:5824`. NullRHI включается `-nullrhi` или токеном режима (`Engine/Src/DynamicRHI.cpp:60`), звук отключает `-nosound`. Первая проверка (2026-10-30, Wine + Xvfb, `DLC_Intro_Persistent`, `-nosound -unattended -forcelogflush`):

- Движок запустился в `NetMode 1` с NullRHI и классом игры `OLGame`, загрузил карту и потоковые уровни без критических ошибок.
- Процесс проработал 100 с до принудительной остановки. RSS 572 МБ, после загрузки около 10% одного ядра.
- `?ListenPort=` не подействовал: сокет занял порт 7777. Для нескольких комнат это нужно исправить.
- Это карта меню: ботов, сюжетной карты и частоты тика проверка не покрывает. Лог заканчивается на 6-й секунде, поэтому работу цикла подтверждают только жизнь процесса и расход CPU.

### 5. Два клиента и сервер без окна

На основе `launchClient1.sh` и `launchClient2.sh` с `-nosound -nomovie` под `xvfb-run` (установлен) или виртуальным десктопом Wine. D3D9 под Xvfb потребует программной реализации или DXVK с lavapipe, это нужно проверить. Сценарий: подтвердить или опровергнуть дублирование врагов и пройти сценарии триггеров без участия человека.

### 6. Командный канал

Для внешнего редактора уже есть Unix socket → `GUnrealEd->Exec`. Тот же подход даёт тестам возможность выполнять Exec-команды и получать ответ. Без него пункт 5 управляется только сценарием на карте.

### 7. Детерминизм

Фиксированный seed ИИ и спавна, фиксированный шаг времени. Без этого сценарии дерева поведения и зрения нестабильны. Шаг времени в UE3 задаётся `-fixedseed` и `-fps`/`-deterministic`; поддержку нужно проверить на этой сборке.

### 8. Визуальные регрессии

Снимок backbuffer D3D9 и сравнение с эталоном с допуском. Для артефактов SkeletalMesh и поворота Dummy. Дорого и хрупко, поэтому в конце.

### Встроенные проверки

В `Multiplayer/ARCHITECTURE_CENTRALIZED.md` (раздел 13) предусмотрена отладочная команда сверки: хэш мира на сервере и на клиенте. Она дешевле большинства пунктов выше и заменяет много ручных проверок рассинхрона.
